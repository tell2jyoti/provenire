SECTION 01

Scope & context

This document specifies how Provenire (see PRD v1.1) is engineered and deployed for Phase 1: the free, open MCP security scanner plus the foundations of the paid control plane.

It makes the explicit buy-vs-build decisions, selects AWS components, costs the deployment, defines the scanner engine and API, and sets the security and reliability posture. Phase 1 is framework-neutral: it ships the scanner plus a single generic baseline mapping pack. The mapping engine is data-driven, so Phase 2/3 features (named-framework packs, continuous monitoring, enforcement proxy) are designed for and add as data, not as engine rewrites. The governing constraints from the owner are honoured throughout: EC2 for dev and prod; build only the core engine; buy the rest; do not over-invest in load balancing or observability; stay in budget so the free tier can ship.

v1.1 amendment

Revised for the horizontal-first decision: the mapping layer is now a data-driven pack engine with a hard detection/mapping boundary. §08 (mapping subsystem), §04 (buy-vs-build), §07 (engine emits neutral findings), §09 (data model uses pack id/version) and §10 (evidence endpoint takes packs) carry the change.

SECTION 02

Design principles

  • Build the moat, rent the plumbing. Engineering effort goes only into the scanner engine, the control-mapping engine, and evidence generation — the parts no vendor sells. Everything generic is a managed service or off-the-shelf.
  • Budget is a hard constraint, not an aspiration. Phase 1 must run for the price of one small instance so the scanner can be free. Any component that adds a fixed monthly fee must justify itself or be deferred.
  • Don't gold-plate the free tier. The free/public tier accepts a single box and best-effort uptime. High availability, autoscaling, and load balancing are deferred to the paid Compliance tier where they're paid for.
  • Deterministic by default. The free engine uses no LLM, so it has zero per-scan cost and no data-egress risk. Models are an opt-in, paid-tier layer.
  • Security is a Phase-1 requirement, not a later hardening pass. A scanner that dials arbitrary URLs is itself an attack tool; SSRF defence ships in v1 (see §11).
SECTION 03

System architecture

Logical view of Phase 1. The portal UI is static and hosted off-box; one EC2 instance runs the API, engine, and reverse proxy; managed services hold state. Target MCP servers are reached only through a restricted-egress path.

Request flow (scan): browser → Netlify UI → Caddy → Scanner API → Engine connects to the target over streamable-HTTP, enumerates tools/resources/prompts, runs detection, returns a scored result; report artifact written to S3, run metadata to Postgres. The CLI bypasses the portal entirely and runs the same engine locally (the only path that can scan stdio servers and private/regulated servers).

SECTION 05

AWS deployment topology — Phase 1

  • Region: ap-south-1 (Mumbai) for owner proximity, or us-east-1 for lowest list price. Pricing below uses us-east-1; Mumbai runs ~10–15% higher.
  • Instance: one EC2 t4g.small (2 vCPU / 2 GiB, Graviton/ARM). Python/Node run on ARM unchanged. Drop to t4g.micro if traffic is light; size up vertically before ever adding a second box.
  • On the box (Docker Compose): Caddy (TLS + routing) · Scanner API · Control API · Engine workers. One docker compose up is the entire deploy.
  • Storage: 20 GB gp3 EBS root; nightly EBS snapshot (cheap). Reports/evidence in S3 with versioning on.
  • State: Neon Postgres (external, managed). Phase-1 hosted DB holds public-scan data only — no regulated data ever reaches hosted infra (that path is CLI/self-host).
  • Network: security group exposes only 80/443 inbound; the scan worker runs with egress filtered to deny link-local (169.254.169.254) and RFC-1918 ranges (see §11).
  • Identity: instance role with least-privilege IAM (S3 prefix + SSM read + CloudWatch put only). IMDSv2 enforced, hop limit 1.

Budget verdict

Phase 1 lands at ~$16–20/mo on-demand (less reserved), comfortably inside "ship it free." A new AWS account's 12-month free tier (750 micro-hrs + 30 GB EBS) makes year one cheaper still. Recommendation: start on-demand (no commitment pre-PMF); switch to a Savings Plan once traffic is steady. Mumbai region adds ~10–15%.

The only cost that can scale unexpectedly is the optional semantic layer — fenced to paid tiers, off by default, and cached by manifest hash so unchanged tools never re-invoke a model.

SECTION 07

Scanner engine — the build

Pipeline

  1. Connect — MCP SDK ClientSession over streamable_http (hosted) or stdio (CLI only). initialize() handshake with timeout.
  2. Enumerate — list_tools(), list_resources(), list_prompts(). Scanning all three, not tools alone, is a deliberate coverage choice.
  3. Normalize — capture each tool's name, description, input schema; compute a stable manifest hash for drift detection.
  4. Detect — deterministic rules + YARA-style patterns for: poisoning/hidden-directive text, invisible unicode, exfil patterns, over-privileged primitives (shell/file/SQL/egress), missing/unbounded schema validation, tool-name shadowing/collision.
  5. Score — normalized severity + confidence + rationale per finding; "intended behaviour" suppression to hold signal.
  6. Emit — JSON result + rendered HTML report; persist run + hash; (paid) hand to mapping engine.
# engine connect + enumerate (streamable-HTTP, hosted path)
async with streamable_http_client(url) as (r, w, _):
    async with ClientSession(r, w) as s:
        await s.initialize()
        tools     = await s.list_tools()
        resources = await s.list_resources()
        prompts   = await s.list_prompts()
        # → normalize → detect → score → emit

The engine emits framework-neutral findings — it never names a regulation. Engine, rules, and CLI are open source; the mapping engine, the packs, the evidence store, and the reputation index are the commercial control plane (open-core boundary from PRD §10).

SECTION 08

Mapping & evidence subsystem

Two layers, deliberately decoupled, so domains are added as data:

  • Detection (framework-neutral). The engine emits Finding records keyed by a stable finding_type (e.g. tool.poisoning, tool.over_privilege, audit.no_immutable_log). No regulation is referenced here.
  • Mapping (data-driven packs). The mapping engine loads a versioned pack — a declarative file that maps finding_type → one or more controls. It emits ControlState records. Swapping or adding a pack changes the output; the engine code does not change.

Phase 1 ships exactly one pack — baseline — proving the architecture end to end. SOC 2, HIPAA, PCI-DSS and ISO packs are added in Phases 2–3 as new files under packs/.

# packs/baseline.yaml  (Phase 1)  — declarative, no engine code
pack: baseline
version: 1
maps:
  - finding_type: tool.over_privilege
    control: baseline.least_privilege
    status_when_present: fail
  - finding_type: audit.no_immutable_log
    control: baseline.audit_logging
    status_when_present: fail
# packs/soc2.yaml (Phase 2) reuses the same finding_types → CC6.1, CC7.2 …
  • Runtime mapping is deterministic — auditors require reproducibility. Any LLM help is confined to authoring packs offline, never to producing a live assertion.
  • Both failing and passing controls produce evidence (auditors need proof of what holds, not only gaps).
  • Packs are versioned; each EvidencePack records the pack id + version it was generated against, so evidence is traceable as packs evolve.
  • Evidence packs are export artifacts (JSON + rendered PDF/HTML) suitable for GRC import and auditor hand-off.

S3 — artifacts

  • reports/{scan_id}.html|json — human + machine reports.
  • evidence/{pack_id}.zip — signed evidence bundles (versioning on).
  • manifests/{server_hash}/{ts}.json — manifest snapshots for drift diffing.

Append-only audit semantics: scan_run, finding, control_state are never updated in place — re-scans insert new rows, preserving the timeline an auditor needs.

SECTION 11

Security architecture

Primary threat — SSRF via the scanner itself

A service that connects to user-supplied URLs is a server-side request forgery weapon if unguarded: an attacker could point it at the EC2 metadata endpoint or internal hosts. This is a P0 mitigation, shipping in v1.

  • Block dangerous targets — reject link-local (169.254.0.0/16, incl. metadata), loopback, and RFC-1918 ranges at request validation; re-resolve DNS and re-check to defeat rebinding.
  • Constrain egress — the scan worker's egress is filtered to public destinations only; it cannot reach the instance metadata service or VPC-internal addresses.
  • IMDSv2 enforced, hop limit 1 — even a successful SSRF cannot read instance credentials.
  • Hard timeouts & concurrency caps — 10s per scan, bounded parallelism; a slow/malicious target cannot exhaust the box.
  • Least-privilege IAM — instance role limited to its S3 prefix, SSM read, CloudWatch put; nothing else.
  • Secrets in SSM Parameter Store, never in images or env files in the repo.
  • Data boundary — hosted service scans public servers only; private/regulated servers use the CLI/self-host path so manifests never leave the customer's network.
SECTION 12

Reliability & scaling — explicit trade-offs

The free tier deliberately runs as a single box with best-effort uptime. This is a conscious decision, not an oversight: the PRD's reliability and high-availability guarantees attach to the paid Compliance tier, which is where customers pay for them.

SECTION 13

Observability & CI/CD

  • Observability (bought, minimal): CloudWatch for app logs + basic metrics; a free external uptime monitor (UptimeRobot / Better Stack) for the public endpoint. No custom dashboards, no self-hosted Grafana in Phase 1 — per the no-over-investment constraint.
  • CI/CD: GitHub Actions builds and pushes the Docker image, then deploys to EC2 via SSM Run Command (no inbound SSH needed). One workflow, free tier.
  • Environments: dev runs the same Docker Compose locally or on a second cheap instance; prod is the t4g.small. Identical compose file = no environment drift.
SECTION 14

Risks, QA review log & open questions

QA review log — caught & resolved before v1.0

QA-T1 · resolved

SSRF: hosted scanner could be aimed at metadata/internal hosts. → §11 mitigations made P0 (IP blocking, egress filter, IMDSv2 hop-limit 1).

QA-T2 · resolved

stdio servers run as local subprocesses and can't be scanned remotely. → Hosted = streamable-HTTP/SSE only; stdio is CLI-only (also the private-server path).

QA-T3 · resolved

Single EC2 contradicts PRD reliability NFRs. → Explicit trade-off (§12): free tier best-effort; HA is a paid-tier feature.

QA-T4 · resolved

Synchronous scan could hang a worker. → 10s hard timeout + concurrency cap; queue deferred to scale path.

QA-T5 · resolved

1-yr reserved commitment pre-PMF is premature. → Budget defaults to on-demand; Savings Plan only after steady traffic.

QA-T6 · resolved

Managed DB egress vs regulated data. → Phase-1 hosted DB stores public-scan data only; regulated path is CLI/self-host (consistent with PRD FR-05).

Open questions

  • OQ-T1 Region: ap-south-1 (latency/owner) vs us-east-1 (price)? ~10–15% delta.
  • OQ-T2 Egress filtering mechanism: security-group + app-level IP checks vs a small egress proxy — which is simplest to operate on one box?
  • OQ-T3 Engine licence: clean-build vs forking an OSS scanner — confirm no copyleft entanglement with the commercial control plane (links to PRD OQ-5).
  • OQ-T4 Neon free-tier limits (compute hours, storage) vs expected scan volume — validate headroom before launch.
