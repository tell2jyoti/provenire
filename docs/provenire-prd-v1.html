SECTION 01

Executive summary

Regulated companies are wiring AI agents into their core systems through the Model Context Protocol (MCP), and they cannot prove to an auditor that those agents are safe to operate. Provenire closes that gap.

MCP has become the default way to connect AI agents to tools, databases, and SaaS. It is spreading fastest exactly where it is most dangerous — healthcare, financial services, insurance — because those sectors have the most valuable data and the strictest audit obligations. The protocol authors deliberately left security to implementers, so every MCP server an enterprise adds is an unvetted path into a regulated system.

Two tool categories exist today, and neither solves the regulated buyer's actual problem. MCP security scanners (Snyk Agent Scan, Cisco mcp-scanner) find vulnerabilities but emit engineer-facing findings, not auditor-facing evidence. GRC compliance platforms (Vanta, Drata, Secureframe) emit audit evidence but have no concept of MCP, tool descriptions, or agent permissions. The regulated buyer is forced to bridge the two by hand, in spreadsheets, before every audit.

Provenire is the bridge. It scans live MCP deployments for the known attack classes, then maps each finding and each granted permission to the control it satisfies or violates — and exports the result as an audit-ready evidence pack. The free, open scanner drives adoption; the paid control plane (continuous monitoring, drift detection, control-mapped evidence, immutable audit log) is the business.

Sequencing — horizontal first, vertical later. Phase 1 ships framework-neutral: the scanner plus a generic baseline control-mapping pack that gives any MCP deployment value without committing to a named regulation. The mapping layer is data-driven, so named-framework packs — SOC 2, then HIPAA, then PCI-DSS, then ISO 27001 — are added one per release in Phases 2–3 with no engine changes. Breadth of adoption now; defensible vertical depth as it compounds.

One-line thesis

Scanners tell an engineer a tool is poisoned. Provenire tells a CISO's auditor that the agent touching sensitive data is provably constrained — and produces the paper to prove it. Generically at first; per-framework as the packs ship.

v1.1 amendment

This revision changes the go-to-market sequence from "vertical compliance product at launch" to "horizontal engine + baseline pack at launch, vertical packs in Phases 2–3." The architecture is built to support domains from day one; no single domain is required to ship. Sections 03, 07, 08 and 13 carry the change.

SECTION 02

Problem & background

Why MCP creates a new, unaddressed compliance surface

MCP is now the de-facto integration standard for agentic AI, with protocol SDKs at roughly 97M downloads per month and adoption across the major model providers. The official specification explicitly states it cannot enforce security at the protocol level — that responsibility shifts entirely to whoever deploys the server.

The resulting exposure is measured, not hypothetical. Independent scans of public MCP servers have found tool-poisoning payloads present in roughly 5% of servers, and individual MCP-related CVEs have reached the maximum CVSS 10.0 severity. The marquee attack classes are specific to MCP:

  • Tool poisoning — malicious instructions hidden in a tool's description, which the agent reads as ground truth and obeys.
  • Rug-pulls — a server changes a tool's behaviour silently after it has been approved and installed.
  • Cross-origin / tool shadowing — one server's tool overrides or impersonates another's.
  • Over-privileged tools & weak schemas — tools exposing shell, file mutation, or raw query access with no input bounds.

Why this is a compliance problem, not only a security problem

In regulated sectors the obligation is not just to be secure but to demonstrate it. Procurement in healthcare, finance, and insurance now demands SOC 2 Type II, HIPAA BAAs, and PCI-DSS attestations on the day a contract is signed — and regulators expect immutable records of every agent action, retained for up to seven years in financial services. When an AI agent reads a record through MCP, it inherits every one of those obligations.

The gap, precisely

A security scanner output ("tool X contains a suspicious description") is not an audit artifact. No framework has a control that says "run a scanner." Auditors ask: which control does this satisfy, what is the evidence, and how do you know it is still true today? Nothing on the market answers that for MCP.

SECTION 03

Goals & non-goals

Goals

G1 · Wedge

Become the default free tool a regulated developer runs before approving an MCP server.

G2 · Bridge

Convert raw MCP findings into control-mapped, audit-ready evidence via a data-driven mapping layer — a generic baseline pack first, named-framework packs added without engine changes.

G3 · Continuity

Prove a deployment is still compliant over time via drift & rug-pull detection.

G4 · Trust

Keep regulated data inside the customer boundary by default; earn the buyer's trust posture.

G5 · Moat

Accumulate an MCP server reputation & control-evidence graph that compounds with usage.

G6 · Extensible

Make the mapping layer pluggable so each new regulated domain ships as a self-contained pack — vertical depth without re-architecture.

Non-goals (Phase 1)

  • Not a general-purpose GRC platform. Provenire produces MCP/agent evidence that feeds Vanta/Drata; it does not replace them in year one.
  • Not domain-specific at launch. Phase 1 is framework-neutral — a buyer gets value from the scanner and the baseline pack without adopting any named regulation. Vertical depth (SOC 2 → HIPAA → PCI-DSS → ISO) arrives as packs in Phases 2–3, not in v1.
  • Not racing Snyk on IDE/client breadth. The wedge is the bridge (findings → control evidence) and, later, vertical depth — not feature parity on scanning surface.
  • Not a runtime model firewall or guardrail engine for prompt content. Scope is the MCP tool/permission surface, not message-level moderation.
  • Does not "certify" compliance. It produces evidence; the auditor and the customer's controls determine certification.

SECTION 08

The control-mapping model — pluggable packs

Generic control-mapping exists in GRC platforms, so the defensible idea is not "we map to controls" — it is where the mapping sits and how it extends. Two layers, kept strictly separate:

  • Detection layer (framework-neutral). The engine produces facts about an MCP server — this tool exposes shell access, this description is poisoned, no immutable record exists. These facts mention no regulation.
  • Mapping layer (data-driven packs). A versioned pack turns a fact into "satisfies / violates control X." Phase 1 ships a generic baseline pack; named-framework packs are added later as data, not code.

Because the boundary is hard, adding a regulated domain is dropping in a new pack — no change to the detection engine. That is what makes "horizontal now, vertical later" an architecture rather than a rewrite. Illustrative output of named-framework packs (Phases 2–3), built on the same neutral facts:

MCP fact / finding (neutral)RiskPack maps it toEvidence produced

In Phase 1 the same neutral facts run through the baseline pack, producing generic control evidence (least-privilege, change-control, audit-logging, injection-resistance) that any MCP deployment can use. Packs are versioned and centrally maintained: as the MCP spec or a regulation evolves, the pack updates and every customer's evidence references the pack version it was generated against. Both failing and passing controls produce evidence — auditors need proof of what works, not only a list of what is broken.

SECTION 10

System architecture & data model

Component stack

  1. Scanner engine (Python, official MCP SDK as client) — connection, enumeration, deterministic + rule checks. Shipped as CLI/Docker and as the hosted portal backend.
  2. Control-mapping service — applies the maintained mapping library to engine findings; produces control states.
  3. Evidence store — append-only, tamper-evident; holds findings, control states, manifest hashes, timestamps. JSON from day one (the data is the moat even before a DB wraps it).
  4. Control plane (SaaS) — scheduling, drift detection, dashboards, evidence export, reputation index, SIEM/OTel egress.
  5. Enforcement proxy (P2) — optional runtime data-plane sitting beside customer MCP servers.

Open-core boundary

Engine + CLI + enforcement proxy are open source (drives trust and adoption, resists "just a wrapper" criticism). Control-mapping library, evidence store, drift, reputation index, and audit log are the commercial control plane. Value and lock-in sit in the control plane and the data — not the forkable proxy.

Core entities

  • Server — endpoint, transport, owner, trust state, manifest-hash history.
  • Tool / Resource / Prompt — description, schema, privilege flags, version hash.
  • Finding — type, severity, confidence, rationale, linked entity.
  • ControlState — framework, control id, status (pass/fail/NA), evidence ref, asserted-at.
  • EvidencePack — framework, scope, generated-at, signature, included control states.
  • ScanRun — trigger, actor, duration, diff vs. previous run.
SECTION 11

Provenire's own compliance posture

A product that sells compliance evidence is held to a higher bar than its customers. Non-negotiables:

  • Default to no-egress for regulated data; PII/secret redaction occurs before any data could leave the customer boundary, never at a downstream model provider.
  • Own SOC 2 Type II + HIPAA readiness on the roadmap before Compliance-tier GA; BAA available; report artifacts signed.
  • Immutable, exportable audit log with up-to-7-year retention to match financial-services expectations.
  • Honest claims — marketing says "audit-ready evidence" and "maps to controls," never "guarantees compliance." Overclaiming is an existential legal risk for this category.

Glossary

MCP — Model Context Protocol, the standard connecting AI agents to external tools/data. Tool poisoning — malicious instructions hidden in a tool description. Rug-pull — silent post-approval change to a tool. Evidence pack — framework-organized, timestamped audit artifact.
