SECTION 01

The mental model

VS Code is a window. The work lives on an always-on EC2 box. Claude Code does the typing; you keep the vision and the final judgment. Every feature passes an adversarial review panel before it touches git.

Four rules anchor everything below:

  • One feature = one branch = one tmux session. Work is isolated and survives you closing the laptop.
  • Test-first is law. No production code is written until a failing test exists for it. The detection-rules spec is the source of those tests.
  • The agent writes; subagents review. An architect, a code-reviewer, a security-reviewer, and a QA agent each attack the work from one angle. They are read-only by design — a reviewer cannot approve its own edits.
  • "Done" is defined, not declared. A feature is done only when tests are green, all reviewers pass, and you have read the diff. You are the author of record.
  • Detection is framework-neutral; mapping is data. The engine never names a regulation — it emits findings. Control mapping lives in pack files. Domains are added as packs, not code.

v1.1 amendment

Updated for horizontal-first: the repo now separates a framework-neutral engine from a data-driven packs/ layer, ships a baseline pack in Phase 1 (F8), and adds a mapping-pack-spec.md alongside the detection spec. §03 (repo tree), §04 (CLAUDE.md) and §09 (backlog) carry the change.

SECTION 02

Machine setup (one time)

This is the Vizuara workflow mapped to Provenire. Heavy compute isn't the point here (no GPUs needed — this is CPU work), so the dev box can be small and stopped when idle.

  1. EC2 (Ubuntu). Launch a small instance — a t4g.small mirrors the production target and runs the engine + tests comfortably. Create and save the key pair; allow inbound SSH (22) from your IP; attach an Elastic IP so the address is stable. Set a billing alert on day one.
  2. VS Code Remote-SSH. Add the box to ~/.ssh/config as Host provenire-dev, then Remote-SSH: Connect to Host. Your editor and terminal now run on the server.
  3. tmux + Claude Code on the server. sudo apt install tmux; install Claude Code with the native installer; start a session per feature.
  4. Secrets as env vars, never in code. AWS keys, the Neon connection string, and any model key go in a project .env that is git-ignored — enforced by a hook (§07).
# on the EC2 box
sudo apt update && sudo apt install -y tmux git
curl -fsSL https://claude.ai/install.sh | bash
tmux new -s feat-connect      # one session per feature
cd provenire && claude        # Claude Code reads CLAUDE.md on launch

Guardrail

Stop the dev instance when idle (a stopped box bills only for disk). The two classic surprise bills are an idle instance and a leaked key in git history — the hooks in §07 defend the second; the billing alert defends the first.

SECTION 03

Repository structure

The open-core boundary from the TDD becomes directories, so licensing is unambiguous: OPEN Apache-2.0, COMMERCIAL proprietary. Tests live beside the code they cover; the spec and fixtures are first-class.

provenire/ ├── CLAUDE.md # root constitution — read every session ├── README.md · pyproject.toml · uv.lock ├── .gitignore · .env.example ├── docs/ │ ├── prd.html · tdd.html │ ├── detection-rules-spec.md # framework-NEUTRAL findings → test source │ ├── mapping-pack-spec.md # the pack file format (finding_type → control) │ └── adr/ # architecture decision records ├── .claude/ │ ├── settings.json # hooks: pre-commit test gate, secret block │ ├── agents/ # the review panel (read-only) │ │ ├── architect.md · code-reviewer.md │ │ ├── security-reviewer.md · qa.md │ ├── skills/ # /feature, /tdd-red, /review, /commit │ │ └── feature/SKILL.md │ └── hooks/ │ ├── pre-commit-tests.sh · block-secrets.sh ├── .mcp.json # dev-time MCP servers for Claude Code ├── packages/ │ ├── engine/ OPEN # the core build │ │ ├── src/provenire_engine/ │ │ │ ├── connect/ # MCP client: stdio + streamable-http │ │ │ ├── enumerate/ · detect/ · score/ · report/ │ │ └── tests/ # test-first lives here │ │ ├── fixtures/ # vulnerable sample manifests │ │ └── unit/ · integration/ │ ├── cli/ OPEN # wraps the engine │ └── control_plane/ COMMERCIAL # mapping engine · packs · evidence · API │ ├── src/.../mapping/ # data-driven: loads packs, emits ControlState │ ├── src/.../evidence/ · api/ # FastAPI │ ├── packs/ # baseline.yaml (P1); soc2/hipaa/pci.yaml (P2-3) │ └── tests/ ├── fixtures-servers/ # runnable deliberately-vulnerable MCP servers ├── infra/ # Caddyfile · docker-compose · deploy └── .github/workflows/ci.yml # re-runs full suite on push

Why this shape

Nested CLAUDE.md files can sit inside engine/ and control_plane/ for local context. The fixtures-servers/ are real MCP servers with planted vulnerabilities — both your test targets and, later, a public asset that markets the scanner. Critically, detection and mapping never mix: the engine emits framework-neutral findings, and control_plane/packs/ turns them into controls as data. Adding a regulated domain in Phase 2-3 is a new file under packs/ — never an engine change.

SECTION 04

Claude Code context files

CLAUDE.md — the constitution

Read on every session start. Keep it tight; long reference material belongs in skills (loaded on demand), not here.

# Provenire — Agent Constitution

## What this is
MCP security + compliance-evidence platform. Open-core:
- packages/engine, packages/cli  → Apache-2.0 (OPEN)
- packages/control_plane          → proprietary (COMMERCIAL)
Never import control_plane from engine/ or cli/.

## Architecture law: detection ≠ mapping
The engine emits FRAMEWORK-NEUTRAL findings (finding_type only).
It must never name a regulation. Mapping to controls happens
only in control_plane/packs/*.yaml (data, not code). Adding a
domain = a new pack file. If you're tempted to write "if HIPAA"
in the engine, stop — it goes in a pack.

## The law: test-first
No production code without a failing test first.
Detection tests derive from docs/detection-rules-spec.md;
pack tests from docs/mapping-pack-spec.md. If a behaviour
isn't in a spec, stop and ask — do not invent rules.

## Commands
test:  uv run pytest -q
lint:  uv run ruff check . && uv run mypy .
run:   uv run provenire scan <url>

## Definition of done
green tests + code-reviewer pass + security-reviewer pass
+ qa pass + human read the diff. Only then commit.

## Security rules (this is a security product)
- Scanner must block link-local (169.254.0.0/16) & RFC-1918 targets.
- Never commit secrets. Keys live in .env (git-ignored).
- Hosted path scans public servers only; stdio = CLI only.

## Commit format  feat|fix|test|chore(scope): summary

A review subagent — .claude/agents/security-reviewer.md

The body of an agent file is a system prompt, not a user message. Reviewers are read-only (no Edit/Write/Bash) and run on a cheap model.

---
name: security-reviewer
description: Adversarial security review of a diff. Use before any commit.
tools: Read, Grep, Glob        # read-only: cannot edit or run commands
model: haiku
---
You are a hostile application-security reviewer for a security product.
Assume the code is vulnerable until proven otherwise. For this diff, hunt:
- SSRF: can a user-supplied target reach 169.254.169.254 or RFC-1918?
- Secrets committed, logged, or echoed.
- Over-broad tool/permission or missing input-schema validation.
Output: ordered list of concrete findings by severity, and the exact
change required to clear each. If you find nothing, say why you're confident.
Never praise. A review that only praises is worthless.

The feature skill — .claude/skills/feature/SKILL.md

---
name: feature
description: Run the full test-first feature loop end to end.
argument-hint: [feature-name]
---
Drive feature "$1" through the loop in docs (Build Blueprint §06):
1. Spawn the architect subagent → design + ordered TEST LIST + acceptance criteria.
2. Write those tests FIRST. Run them. Confirm they FAIL (red). Show me the red.
3. Write the minimum code to pass. Run. Confirm green.
4. Refactor; tests stay green.
5. Spawn code-reviewer, security-reviewer, qa subagents on the diff.
6. Fix every finding; re-run reviews until clean.
7. Stop and ask me to read the diff before committing.

SECTION 05

The agent panel

SubagentLensRunsTools
architectDesign the feature; emit the test list & acceptance criteria from the specStart of each featureRead-only
code-reviewerQuality, correctness, readability, edge cases, dead codeAfter greenRead-only
security-reviewerSSRF, secrets, over-privilege, schema gaps (it's a security product)After greenRead-only
qaDo tests actually cover the spec? Were they red first? Run full suite; try to break itBefore commitRead-only

All four are read-only and use a cheap model — the parent (main) agent, running on your stronger model, is the only writer. This isn't a limitation to work around; it's the safeguard. A reviewer that could edit could quietly fix-and-approve, defeating the gate.

SECTION 06

The per-feature loop

Invoked with /feature connect-enumerate. The red and green steps are the heart of TDD.

1
Architect. Subagent reads the spec + TDD doc and returns a design, an ordered test list, and acceptance criteria. No code yet.
2
Red. Main agent writes the tests first and runs them. They must fail. RED The failing run is shown to you — proof TDD wasn't faked.
3
Green. Main agent writes the minimum code to pass. Suite goes green. GREEN
4
Refactor. Clean the code; tests stay green.
5
Review panel. code-reviewer + security-reviewer + qa subagents attack the diff in parallel and return ordered findings.
6
Resolve. Main agent fixes every finding; reviewers re-run until clean.
7
Human gate. You read the diff. Anything you can't stand behind comes out.
8
Commit & close. The pre-commit hook re-runs tests deterministically; on green, commit and mark the feature/issue done.
SECTION 07

Deterministic gates (hooks)

Reviewers are smart but probabilistic; hooks are dumb but certain. Use hooks for the rules that must always hold. A PreToolUse hook on the commit denies it (exit code 2) if tests are red — the model cannot argue past it.

// .claude/settings.json
{ "hooks": {
  "PreToolUse": [
    { "matcher":"Bash", "hooks":[
      { "type":"command", "command":"$CLAUDE_PROJECT_DIR/.claude/hooks/block-secrets.sh" },
      { "type":"command", "command":"$CLAUDE_PROJECT_DIR/.claude/hooks/pre-commit-tests.sh" }
    ] }
  ]
} }
# pre-commit-tests.sh — deny commit if fast tests fail
cmd=$(jq -r '.tool_input.command')
if echo "$cmd" | grep -q 'git commit'; then
  uv run pytest -q -m "not slow" || { echo "tests red — commit blocked" >&2; exit 2; }
fi
exit 0
  • block-secrets.sh — scans the staged diff for key patterns (AWS, Neon URL, tokens) and denies on a hit. Defends the classic leaked-key surprise bill.
  • Fast vs full — the commit hook runs fast unit tests only; the full suite (incl. integration against fixture servers) runs in GitHub Actions on push, so commits stay quick.
SECTION 08

Git & feature workflow

  • Branch per feature: feat/connect-enumerate, one tmux session, one /feature run.
  • Conventional commits (feat|fix|test|chore(scope): …) so history is machine-readable and CI/changelogs are trivial later.
  • Squash-merge to main after the panel passes and you've read the diff. main stays releasable.
  • CI on push (GitHub Actions, free tier) re-runs the full suite including integration against fixtures-servers/ — the safety net behind the local fast-test hook.

SECTION 10

QA review log & open questions

QA-B1 · resolved

Reviewer subagents can't edit (they're read-only by design). → Panel is review-only; the main agent does all writes and resolves findings. Stated explicitly so no one builds a "coder subagent" that can't approve itself.

QA-B2 · resolved

TDD-honesty trap: agent writes code then back-fills a passing test. → Architect emits the test list first; the red step must show failing tests before green; qa verifies red-before-green.

QA-B3 · resolved

"Done" gets self-declared early. → Definition of done is explicit in CLAUDE.md (green + 3 reviews + human read).

QA-B4 · resolved

Full suite on every commit is slow. → Hook runs fast unit tests; full/integration runs in CI on push.

QA-B5 · resolved

Secret leakage into git. → block-secrets PreToolUse hook + .env git-ignored + env-var-only keys.

QA-B6 · resolved

Cost/context bloat. → Reviewer subagents on a cheap model in isolated context; strong model reserved for the main coding agent.
